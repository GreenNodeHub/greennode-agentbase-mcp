Token Benchmark

A meta-tool gateway beats a flat 116-tool manifest — by 7–41% fewer tokens per session.

Two variants of the AgentBase MCP server — a 3-tool meta-tool gateway backed by BM25 search, and a naive flat baseline exposing all 116 operations directly — compared on manifest size, latency, and end-to-end token cost. Under z-ai/glm-5.2, with the CLI escape hatch closed, the gateway wins all four tasks.

Model · z-ai/glm-5.2 Suite · 4 tasks × 2 variants Endpoints · dev (deployed) Date · 2026-07-06
01Summary

The gateway's value is amortization, not per-call efficiency.

The flat baseline was built as a deliberately naive reference point to quantify the "MCP tax" the gateway exists to avoid. The headline: flat loads 36.8× the manifest into context, paid every turn — and that fixed cost dominates short-to-medium sessions.

Headline finding. With the model actually using the MCP server (CLI bypass disabled), the gateway wins all four end-to-end tasks by 7% to 41% fewer input tokens, and the win is stable across re-runs (multi-op-same and multi-op-cross both n=2, consistent to within ~1k tokens). The absolute savings grow with op count.
⚠
Methodology trap. An earlier run-set showed "flat won 2 of 3" — that was an artifact. By default the agentbase skill and Bash tool are available, and glm-5.2 bypassed the MCP server entirely by running the greennode CLI. Those runs measured the CLI, not the variants. The clean numbers use --disallowed-tools Bash Skill. See §07.

What each variant pays

The gateway converts a large unconditional fixed cost (a 116-tool manifest every turn) into a small fixed cost (a 3-tool manifest) plus a small per-op premium (a search round-trip). For the access pattern most real sessions have — many available operations, few used — that trade is favorable, and the data confirms it for 1–4 ops under glm-5.2.

Where the gateway wins

  • Fixed manifest — ~397 tokens vs flat's ~14.6k, every turn
  • 1–4-op sessions — wins all four tasks, 7–41% fewer tokens
  • Response sizing — JMESPath fields shrinks a 5.3 KB body to 77 B
  • Worst-case safety — 25 KB cap bounds runaway responses

Where flat is competitive

  • Per-op cost — 1 round-trip vs the gateway's 2 (search + execute)
  • 2-op same-service — smallest gateway margin (7%), flat did it in 1 call
  • Long-task variance — a 4-op gateway run timed out once before completing
  • Simpler model path — direct call, no meta-tool planning needed
02Setup & methodology

Both variants, deployed on dev, sharing one upstream token.

All numbers are live against the deployed runtimes — not localhost. Both variants share the same downstream services and bearer token, so backend latency is identical and not a confound.

Endpoints & auth

  • gateway — endpoint-556ba588-…/mcp (3 meta-tools)
  • flat — endpoint-3491932f-…/mcp (116 tools)
  • Auth — shared bearer token (GREENNODE_MCP_TOKEN), a 30-min JWT forwarded to the same downstream services by both variants
  • Transport — Streamable HTTP, stateless (sessionIdGenerator: undefined); JSON-RPC 2.0 over SSE

How the numbers were taken

Phases 1–2 are direct curl against the endpoints: manifest size from tools/list, latency from n=20 (or n=10 for the 2-round-trip path) sequential calls with curl -w. Phase 3 runs a task suite headlessly via claude -p --output-format stream-json, once per variant, with --strict-mcp-config so only one server is visible per run.

ℹ
Token estimates vs exact counts. Phase 1–2 token figures are bytes/4 estimates (no public Claude tokenizer); JSON-heavy schemas tokenize denser than this, so the 36.8× byte ratio is a floor on the token ratio. Phase 3 numbers are exact client usage, taken from the final result message — the glm backend reports 0 on every assistant turn and aggregates only in result.

The flat baseline's purpose. It is a deliberately naive reference — the "flatten everything into the manifest" design the gateway exists to avoid. It does no search, no projection, no capping. Measuring it against the gateway quantifies the tax the gateway avoids.
04Gateway architecture

A 3-tool router: the model discovers operations by search, invokes them through one execute.

The gateway is a tool router. It exposes exactly three meta-tools and keeps all 116 operations behind a BM25 search index. The operations never appear in tools/list — only the three meta-tools do — which is why the manifest is 1,589 B instead of 58 KB. The model discovers operations by intent, then invokes the one it needs through the single execute tool.

The three meta-tools

ToolArgumentsWhat it does
list_serversnoneReturns the 6 AgentBase services with operation counts and tags. The orient step — cheap, no schemas.
search_toolsquery, server?, limit?BM25 search over the registry. Returns up to limit (default 5) hits, each with the full inputSchema inline — so the model can call execute without a second lookup. Scoped search over-fetches 5× then filters by service, so the post-filter still yields limit hits.
executeid, args?, fields?Looks up the operation by id, calls the downstream service, applies an optional JMESPath fields projection and a 25 KB byte cap. Returns the (possibly projected, possibly truncated) body as text.

Request flow — one logical operation

A single "list my agent runtimes" is three tool calls. The model orients, searches, then executes — and only the search hits' schemas enter context, not all 116.

What the architecture buys

  • Tiny manifest — 3 tools, ~397 tokens, regardless of how many operations exist
  • Schemas on demand — only the search hits' inputSchemas enter context, not all 116
  • Bounded responses — fields + cap keep tool results small
  • Stable surface — the 3-tool manifest never changes as downstream APIs grow

What it costs

  • Extra round-trip per op — search_tools before execute (~1.7× latency, +8 KB)
  • Model depends on search quality — a bad query misses the right operation
  • Meta-tool planning load — the model must sequence list → search → execute; less fluent models spiral
  • Projection is opt-in — the cap guards, but fields only helps if the model uses it
→
This is the explanation for both headline numbers. The 3-tool router is why the gateway's manifest is 36.8× smaller (§05) — the 116 inputSchemas stay out of context until search_tools surfaces them, and only for the hits. And the search-then-execute path is why the gateway's per-op cost is higher than flat's direct call (§06, Phase 2c) — the gateway trades a per-op premium for that manifest saving, and Phase 3 shows the trade pays off for 1–4-op sessions.

06Phase 2 — Latency & response

Per-op, the gateway is heavier — but its real response lever is projection, not the cap.

Three micro-benchmarks isolate the per-call costs. The gateway's manifest savings don't show up here — this is where flat looks strongest. The question is whether flat's per-call edge ever outweighs the manifest tax. (Phase 3 answers: not for 1–4 ops.)

Two findings

  • The 25 KB cap never triggered — the largest real response was 5.3 KB. It's a safety net here, not a daily cost driver
  • The gateway's actual lever is fields: 5,348 B → 77 B, a 69× shrink — but only when the model opts in

Caveat

  • The projection saving is model-behavior-dependent — unlike the manifest tax, it is not unconditional
  • Flat's unbounded responses are a latent risk; unobserved only because this account is sparse

07Phase 3 — End-to-end

With the CLI escape hatch closed, the gateway wins all four tasks.

This is the measurement that actually justifies the gateway — gross input tokens (context pollution) and cache read/write (dollar cost) on identical multi-turn work, taken from the client's own usage.

08Analysis & break-even

Gateway wins when manifest tax saved > discovery premium paid.

The gateway's value is amortization: it trades a large unconditional fixed cost for a small fixed cost plus a small per-op premium. Phase 3 confirms this empirically for 1–4-op sessions.

Break-even

The gateway wins when manifest_tax_saved > discovery_premium_paid. Phase 3 confirms this for 1–4-op sessions: the gateway won all four tasks (7–41% fewer input tokens), with absolute savings growing with op count. The one caveat is variance on longer tasks — a 4-op gateway run timed out once before completing cleanly on retry, so the gateway can spiral under glm-5.2. Where the break-even turns negative (very long sessions, or models that plan meta-tool sequences poorly) remains unmeasured.

→
Honest summary. For the access pattern most real sessions have — many available operations, few used — the gateway's trade is favorable, and the Phase 3 data confirms it for 1–4 ops under glm-5.2. The manifest tax is large enough to dominate short-to-medium sessions; the gateway's risk is long sessions where discovery overhead could accumulate faster than manifest savings.

09Limitations

What this benchmark does and doesn't establish.

  • Phase 1–2 token figures are bytes/4 estimates. JSON schemas tokenize denser than generic text, so the 36.8× byte ratio likely understates the token ratio. Phase 3 numbers are exact client usage.
  • Small-n, but stable where sampled. multi-op-same and multi-op-cross are n=2 with <1k-token variance — the gateway win there is firm. multi-op-long gateway is n=1 completed (a clean win) but with one timeout on a prior attempt; that task is the remaining high-variance cell.
  • The CLI-bypass confound was the dominant measurement risk. The first run-set's "flat won 2 of 3" was an artifact of glm-5.2 escaping to the greennode CLI via Bash+Skill. The clean numbers use --disallowed-tools Bash Skill, now in the harness — anyone re-running must keep it.
  • Model is z-ai/glm-5.2, not Claude. The environment routes claude -p through VNG Cloud MaaS; Claude model names 404 on that backend. glm-5.2 is less meta-tool-fluent and was bypass-prone; Claude may plan more efficiently and extend the gateway's lead. Results do not generalize to Claude without re-running on a Claude model.
  • Prompt caching narrows the dollar gap, not the context-pollution gap. Cached tokens still occupy context window. cache_read is large in every run (e.g. gateway single-op: 48k of 74k input was cache-read). Under caching, flat's manifest is partly amortized too, which is why cost deltas are smaller than gross-input deltas.
  • Account is sparse. No response exceeded 5.3 KB, so the 25 KB cap's behavior is inferred, not exercised. Flat's unbounded-response risk is real but unobserved here.
  • Long-task variance. The gateway won the 4-op task cleanly (n=1) but timed out on a prior attempt. Where the gateway's discovery spirals into unprofitable territory for glm-5.2 is unknown — a 6–10-op MCP-only task with a high time cap would locate the ceiling.
ℹ
Still open. A completed multi-op-long variance set, a Claude-model run, and a 6–10-op probe to find where (if ever) the gateway's discovery overhead overtakes the manifest savings. The harness is ready for all three with a fresh token.
