# Benchmark: gateway (meta-tools) vs flat (one-tool-per-op) — 2026-07-06

Comparison of the two MCP server variants in this repo, run against the deployed
dev endpoints. The flat variant exists *as a baseline* to quantify the "MCP tax"
the gateway is designed to avoid.

| | gateway | flat |
|---|---|---|
| **Tools exposed** | 3 meta-tools (`list_servers`, `search_tools`, `execute`) | 116 (one per operation) |
| **Discovery** | BM25 search, on-demand | all 116 in manifest |
| **Response handling** | JMESPath `fields` projection + 25 KB cap | raw, unbounded |
| **Per-op round-trips** | 2 (`search` + `execute`) | 1 (direct call) |

## TL;DR

- **Manifest (fixed cost):** flat is **36.8×** the gateway — ~14.6k vs ~397 estimated tokens loaded into context at session start, paid every turn. This is the headline MCP tax.
- **Per-op (variable cost):** the gateway is *more* expensive per op — 2 round-trips and ~8 KB search overhead vs flat's single call.
- **Response size:** the gateway's real lever is `fields` (JMESPath), not the 25 KB cap — projection shrank a 5.3 KB response to 77 B (69×). The cap never triggered because the account's real responses are all ≤5.3 KB.
- **End-to-end (Phase 3, z-ai/glm-5.2, MCP-only):** with the CLI escape hatch disabled, the **gateway wins all four tasks (1–4 ops)** — by 7% to 41% fewer input tokens than flat.
  - `single-op` (1 op): **gateway won** — 74k vs 125k input tokens, $0.43 vs $0.71. Both 3 turns / 2 calls; the manifest tax decided it.
  - `multi-op-same` (2 ops, one service): **gateway won** — 77k vs 83k, $0.42 vs $0.46. Smallest margin (flat did it in 1 call since the list response already carried the detail fields).
  - `multi-op-cross` (3 ops, across services): **gateway won** — 102k vs 126k, $0.60 vs $0.73. Gateway took 6 turns / 5 calls vs flat's 4 / 3, but still came out ahead.
  - `multi-op-long` (4 ops, same service): **gateway won** — 102k vs 130k input tokens, $0.58 vs $0.72 (gateway 7 turns / 6 calls, flat 5 turns / 4 calls). An earlier attempt timed out at 150 s / 30 turns — that was variance, not a ceiling; with a 300 s cap it completed cleanly and won by ~21%.
  - **Critical methodology note:** an earlier run-set showed "flat won 2 of 3" — that was an artifact. The `agentbase` skill (which loads the `greennode` CLI) and the `Bash` tool are available by default, and glm-5.2 frequently bypassed the MCP server entirely by calling `Bash` to run `greennode runtime list/get/…`. Those runs measured the CLI, not the MCP variants. The clean numbers above use `--disallowed-tools Bash Skill` to force MCP-only. See the Phase 3 methodology subsection.
- **Net:** when the model actually uses the MCP server, the **gateway wins all four tasks (1–4 ops)** — by 7% to 41% fewer input tokens — and the win is stable across re-runs (multi-op-same and multi-op-cross both n=2, consistent to within ~1k tokens). The manifest-tax advantage holds across short and medium tasks under glm-5.2. Caveat: small-n, glm-5.2 (not Claude) — see limitations.

## Setup

- **Endpoints** (from `~/.claude.json`, this project's `mcpServers`):
  - gateway: `https://endpoint-556ba588-2efe-4b68-8799-6645bae86e4d.agentbase-runtime.aiplatform.vngcloud.vn/mcp`
  - flat:    `https://endpoint-3491932f-0451-42a7-b6e8-5ba82a03c678.agentbase-runtime.aiplatform.vngcloud.vn/mcp`
- **Auth:** shared bearer token (`GREENNODE_MCP_TOKEN`), 30-min JWT. Both endpoints forward it to the same downstream services → backend latency is identical, not a confound.
- **Transport:** Streamable HTTP, stateless (`sessionIdGenerator: undefined`). `initialize` → `tools/list` / `tools/call`, JSON-RPC 2.0 over SSE.
- **Methodology:** all numbers are live against the deployed runtimes. Latency = n=20 (or n=10 for the 2-round-trip path), sequential, `curl -w`. Token counts are **bytes/4 estimates** (no public Claude tokenizer); JSON-heavy schemas tokenize denser than this, so byte ratios are a *floor* on token ratios. The exact token delta is Phase 3 (below), captured from the client's own `usage`.

## Phase 1 — manifest size (the fixed MCP tax)

`tools/list` on each, data payload only (what a client parses and loads into context):

| variant | tools | data payload | ~tokens (bytes/4) | ratio |
|---|---:|---:|---:|---:|
| gateway | 3 | 1,589 B | ~397 | 1× |
| flat | 116 | 58,479 B | ~14,619 | **36.8×** |

Flat per-tool definition size (bytes): min 135, median 325, mean 502, p95 1,042, **max 7,070**.

Largest flat tools (the manifest is skewed, not uniform — 5 tools ≈ 10% of payload):

| bytes | tool |
|---:|---|
| 7,070 | `gateway__post_api_v1_gateways` (nested `oneOf` create body) |
| 6,291 | `gateway__patch_api_v1_gateways__name_` |
| 1,480 | `runtime__create_1` |
| 1,462 | `runtime__update` |
| 1,077 | `runtime__create` |

**Finding:** the manifest tax is dominated by a handful of large create/update schemas. The gateway pays ~397 tokens once; flat pays ~14.6k every turn, regardless of which ops the session actually uses.

## Phase 2a — per-call latency & bytes (n=20)

| call | variant | med (ms) | p95 (ms) | max (ms) | resp bytes |
|---|---|---:|---:|---:|---:|
| `tools/list` | gateway | 34 | 44 | 44 | 1,577 |
| `tools/list` | flat | 57 | 122 | 122 | 54,321 |
| `tools/call` (list runtimes) | gateway | 52 | 76 | 76 | 1,480 |
| `tools/call` (list runtimes) | flat | 49 | 176 | 176 | 1,480 |

**Findings:**
- `tools/list`: flat is ~1.7× slower median with a 2.8× worse p95 — the 34× larger payload shows up in server-side serialization and network latency, not just token cost.
- `tools/call` (list runtimes): responses are **identical** (1,480 B). The response is small, so the gateway's cap/projection doesn't engage — both variants return the same bytes. Per-call latency is statistically indistinguishable; flat has a fatter tail (p95 176 ms).

## Phase 2b — response size: cap vs projection (largest available op: "list gateways", 5 items)

| path | response bytes |
|---|---:|
| flat (raw, unbounded) | 5,348 |
| gateway (25 KB cap, no `fields`) | 5,348 |
| gateway (`fields="items[*].name"`) | **77** |

**Findings:**
1. The 25 KB cap **never triggered** in this account — the largest real response was 5.3 KB. The cap is a safety net, not a daily cost driver here. (A denser account, or a list-all over a large fleet, would change this — flat's unbounded responses are a latent risk, not an observed one.)
2. The gateway's *actual* response lever is `fields` (JMESPath): 5,348 B → 77 B, a 69× shrink — but only when the model opts to use it. This is a model-behavior-dependent saving, unlike the manifest tax which is unconditional.

## Phase 2c — discovery path: gateway 2 round-trips vs flat 1 (n=10, "list gateways")

| path | round-trips | total latency med (ms) | total bytes |
|---|---:|---:|---:|
| flat (direct call) | 1 | 84 | 5,348 |
| gateway (`search_tools` + `execute`) | 2 | 140 | 13,442 |

**Finding:** per-op, the gateway is **more** expensive — ~1.7× the latency and +8 KB (the `search_tools` response carries each hit's full input schema, limit 5). This is the cost of pay-per-use discovery. The gateway recovers this cost only through manifest savings amortized across a session.

## Analysis — when each variant wins

| Cost component | gateway | flat | Winner |
|---|---|---|---|
| Fixed manifest (per turn) | ~397 tok | ~14,619 tok | **gateway 36.8×** |
| Per-op discovery | +1 round-trip + ~8 KB | 0 | **flat** |
| Per-op response (no projection) | parity | parity | tie |
| Per-op response (with `fields`) | down to 77 B | raw | **gateway** (if used) |
| Worst-case response safety | 25 KB cap | unbounded | **gateway** |

**Break-even:** gateway wins when `manifest_tax_saved > discovery_premium_paid`. Phase 3 confirms this empirically for 1–4-op sessions: the gateway won all four tasks (7–41% fewer input tokens), and its absolute savings grow with op count (~24k at 3 ops → ~28k at 4 ops). The one caveat is variance on longer tasks — a 4-op gateway run timed out once before completing cleanly on retry, so the gateway can spiral under glm-5.2. Where the break-even turns negative (very long sessions, or models that plan meta-tool sequences poorly) remains unmeasured. A session using most of the 116 ops — rare in practice — is the theoretical regime where flat's no-discovery path would favor it, but that's beyond what was tested.

**The honest summary:** the gateway's value is *amortization*, not per-call efficiency. It converts a large unconditional fixed cost (116-tool manifest every turn) into a small fixed cost (3-tool manifest) plus a small per-op premium (search round-trip). For the access pattern most real sessions have — many available ops, few used — that trade is favorable, and the Phase 3 data confirms it for 1–4 ops under glm-5.2.

## Limitations

- **Token estimates (Phases 1–2) are bytes/4.** JSON schemas tokenize denser than generic text (many short tokens for keys/braces), so the 36.8× byte ratio likely *understates* the token ratio. Phase 3's numbers are exact client `usage`, not estimates.
- **Phase 3 is small-n, but stable where sampled.** multi-op-same and multi-op-cross are n=2 with <1k-token variance — the gateway win there is firm. single-op is stable across sessions (gateway ~74k, flat ~125–130k). multi-op-long gateway is n=1 completed (a clean win) but with one timeout on a prior attempt — that task is the remaining high-variance cell.
- **The CLI-bypass confound was the dominant measurement risk.** The first run-set's "flat won 2 of 3" was an artifact of glm-5.2 escaping to the `greennode` CLI via `Bash`+`Skill`. The clean numbers use `--disallowed-tools Bash Skill`. This is now baked into the harness, but anyone re-running must keep it — drop it and the model will bypass the MCP server again, producing invalid (CLI-flavored) numbers. Contaminated streams retained under `/tmp/bench-phase3/raw/`.
- **Model is z-ai/glm-5.2, not Claude.** The environment routes `claude -p` through VNG Cloud MaaS via `ANTHROPIC_BASE_URL`; Claude model names (`claude-sonnet-5`, `claude-haiku-4-5`) 404 on that backend, so glm-5.2 was used (also the user's request). glm-5.2 is less meta-tool-fluent than Claude and prone to the bypass above; Claude may plan more efficiently (fewer `search_tools`/`execute` cycles) and extend the gateway's lead, or behave differently on long tasks. Results do *not* generalize to Claude without re-running on a Claude model.
- **Prompt caching** narrows the *dollar* gap (manifest is cacheable across turns) but does **not** narrow the *context-pollution* gap — cached tokens still occupy context window. cache_read is large and active in every run (e.g. gateway single-op: 48k of 74k input was cache-read). Under caching, flat's big manifest is partly amortized too, which is why cost deltas are smaller than gross-input deltas.
- **Account is sparse.** No response exceeded 5.3 KB, so the 25 KB cap's behavior is inferred, not exercised. Flat's unbounded-response risk is real but unobserved here.
- **Long-task variance.** The gateway won the 4-op task cleanly (n=1) but timed out on a prior attempt (30 turns, 150 s). Where the gateway's discovery spirals into unprofitable territory for glm-5.2 is unknown — a 6–10-op MCP-only task with a high time cap would locate the ceiling. The gateway is *designed* for long sessions, so characterizing this ceiling matters for its real-world value.
- **One model, one client, one token TTL.** The 30-min JWT forced batched runs and prevented larger n on the long task. A longer-lived token would enable multi-op-long variance runs and a 6–10-op probe.

## Phase 3 — end-to-end in a client

Ran the task suite headlessly via `claude -p --output-format stream-json`, each against both variants with `--strict-mcp-config` (only one server visible per run). Model: **z-ai/glm-5.2** (the backend this environment routes to via `ANTHROPIC_BASE_URL`; Claude model names 404 here — see limitations). Token: 30-min JWT, shared by both variants. n=1 per cell unless noted.

Usage is taken from the final `result` message — the glm backend reports `0` on every assistant turn and aggregates only in `result`. Cost is the session total (`total_cost_usd`).

### ⚠ Methodology: the CLI-bypass confound (and how it was fixed)

The first run-set produced a "flat won 2 of 3" result that was **wrong**, and the reason matters. By default, `claude -p` exposes the built-in `Bash` tool and the `Skill` tool, and the `agentbase` skill (available in this workspace) loads the `greennode` CLI. When the MCP server's meta-tool discovery felt slow, glm-5.2 **bypassed the MCP server entirely** — invoking the `agentbase` skill and then running `greennode runtime list / get / endpoints / versions` via `Bash`. Those runs measured the CLI, not the MCP variant. An audit of the tool-call sequences showed the majority of gateway runs (and some flat runs) were contaminated this way.

The clean numbers below were produced with `--disallowed-tools Bash Skill`, forcing the model to use only the MCP server. This is the only configuration that actually measures the two variants. **Any future re-run must keep `--disallowed-tools Bash Skill` (already in the harness) or the results will be confounded.** The contaminated streams are retained under `/tmp/bench-phase3/raw/` for reference.

| task | Δinput (mean) | Δcost | Δturns | Δtool_calls | winner | gw savings |

### What this says

With the CLI escape hatch removed, the **gateway wins all four tasks (1–4 ops)** — by 7% to 41% fewer input tokens — and the win is stable across re-runs.

- **`single-op` — gateway won by ~51k (41%).** Both variants took 3 turns. With turn parity, the 14.6k-token manifest tax decided it: flat re-pays the manifest each turn, the gateway doesn't. Cleanest demonstration of the gateway's value.
- **`multi-op-same` — gateway won by ~6k (7%).** Smallest margin. Flat completed the task in 1 tool call (the gateways-list response already carries flavor/replicas/network mode, so no second call needed), while the gateway did `list_servers` + `search_tools` + `execute`. The gateway's extra calls nearly erased its manifest advantage — but the smaller manifest still carried it. Stable across 2 runs (Δ 6.2k / 5.7k).
- **`multi-op-cross` — gateway won by ~24.5k (19%).** Gateway took 6–7 turns / 2–3 calls vs flat's 4 / 2. Despite +2 turns of discovery overhead, the manifest tax still made the gateway cheaper. Stable across 2 runs (Δ 24.7k / 24.3k).
- **`multi-op-long` — gateway won by ~28k (21%).** The 4-op same-service task (list → get → endpoints → versions). Gateway: 7 turns / 6 calls / 102k tokens; flat: 5 turns / 4 calls / 130k tokens. The gateway's absolute savings *grow* with task length here (24k at 3 ops → 28k at 4 ops), supporting the amortization hypothesis. An earlier attempt timed out at 150 s / 30 turns — see variance note.

**The pattern:** for 1–4-op tasks, the gateway's manifest savings outweigh its discovery overhead *even when it takes more turns than flat*. The manifest tax (~14.6k/turn for flat vs ~0.4k for the gateway) is large enough to dominate these sessions. The absolute savings grow with op count (excluding the 2-op outlier where flat got lucky with a single call): ~51k (1 op) → ~24k (3 ops) → ~28k (4 ops). The 2-op dip is task-specific (flat's list response was self-sufficient), not a trend break.

### Variance note

- **multi-op-same** (n=2): gateway 76,904 / 77,541; flat 83,149 / 83,199. Δ within 0.5k. Rock-solid.
- **multi-op-cross** (n=2): gateway 101,756 / 102,699; flat 126,481 / 126,984. Δ within 0.5k. Rock-solid.
- **single-op**: gateway 73,606 / 77,532 (prior); flat ~125–130k across many runs. Stable.
- **multi-op-long** gateway: n=1 completed (101,941). A first attempt timed out at 150 s / 30 turns — high variance on this task (the model can occasionally spiral in meta-tool discovery). The completed run shows the gateway wins decisively when it doesn't spiral, but the timeout is a real risk flag for longer tasks under glm-5.2. n=1, so the magnitude isn't firm.

The earlier wild variance (3–11 turns for "the same" gateway task) was almost entirely the model switching between MCP and CLI; with `--disallowed-tools Bash Skill` the variance collapses to <1k tokens for the medium tasks. multi-op-long is the remaining high-variance cell.

### What's still missing

- **multi-op-long gateway n=1.** The completed run is a clean win, but the first-attempt timeout shows the gateway can spiral on 4-op tasks. More runs would characterize how often.
- **A Claude model run.** The intended client is Claude; glm-5.2 is less meta-tool-fluent and was bypass-prone. The clean MCP-only results are a fair glm-5.2 baseline, but Claude may behave differently (likely extending the gateway's lead if it plans meta-tool sequences more efficiently).
- **Longer sessions (6–10 ops).** The gateway won 1–4 ops, with absolute savings growing. A 6–10-op MCP-only task would confirm the amortization trend continues — and test whether the multi-op-long timeout risk grows with op count.
